# 우리은행 VOC (wrb_voc) 결함 산출물 형식

- 소스: `/volume2/claude/repo/wrb_voc` (브랜치 `wrb_voc_260701ver`, Maven, Spring Boot WAR). 로컬 기동법은 `/volume2/claude/wrb_voc/CLAUDE.md` 의 `wrb-voc-local-run`.
- 참고자료: `/volume2/claude/wrb_voc/` — 분석 문서 `결함분석/`, `개선분석/`, 패키지 `수정소스/`, DB 스크립트 `DB반영/`, 검증 결과 `TEST/`, 원문 일정 `프로젝트관리/`(결함개선 일정 엑셀).
- 기존 예시(형식이 헷갈리면 열어 볼 것): `결함분석/결함34_사전신고_임의종결_결재_분석.docx`, `수정소스/결함34수정_20260825.zip`, `수정소스/결함01_03_09_41_42_43_44수정_20260905.zip`(여러 결함 통합), `수정소스/보안CVE수정_20260913.zip`(증적 포함).

## 1. 분석 문서 — `결함분석/결함NN_<요약>_분석.docx`

개선 건은 `개선분석/개선NN_<요약>.docx`. 파일명 요약은 `화면/기능_증상` 형태로 짧게(예: `결함11_마일리지_중복KEY_JSON에러_분석.docx`).

- **제목(Title)**: `[결함 NN] <결함 제목>`
- **1. 개요** — 4행×4열 표:

  | 결함 순번 | NN | 분류 | 대메뉴 > 중메뉴 > 기능 |
  |---|---|---|---|
  | 조치예정일 | yyyy-MM-dd | 공수 / 우선순위 | 5D / 5 |
  | 분석일 | yyyy-MM-dd | 분석 결과 | 한 줄 결론(원인 특정 여부 · 수정 착수 여부 · 요건 확정 필요 여부) |
  | 소스 기준 | branch wrb_voc_260701ver | 원본 문서 | (위고) 결함개선 일정_조치일.xlsx |

- **2. 결함 내용 (원문)** — 접수 원문 그대로. 고치거나 요약하지 않는다.
- **3. 결론 요약** — 한 문단 결론 + 불릿 3~5개(각 불릿 = 확인된 사실 하나, 근거 포함).
- **4. 동작 구조** — 제목에 관점을 붙인다(예: "4. 동작 구조 (더블클릭 → 상세 → 오류 노출 경로)"). 화면 → Controller → Service → Mapper → 테이블 흐름을 `파일:줄` 과 함께.
- **5. 원인 분석** — `5-1`, `5-2` … 소제목마다 원인 하나. 근본 원인에는 "(핵심 결함)" / "근본 —" 을 붙여 구분. 요건 공백은 별도 소제목.
- **6. 수정 방안** — 제목에 상태를 붙인다: "(미착수, 요건 확정 후 조정)", "(반영 완료 yyyy-MM-dd)" 등. 방안이 여러 개면 A/B 안과 권장안.
- **7. 검증 방법** — 재현 절차와 기대 결과(수정 후 확인 포인트).
- **8. 데이터 정합성 확인 필요** — 이미 오염된 데이터 조회 SQL / 보정 필요 여부. 없으면 "해당 없음" 으로 절은 유지.
- **9. 연관 항목** — 연관 결함·개선 번호와 관계(통합 설계 권장 등).
- **10. 관련 소스 목록** — 경로 + 역할 한 줄.

본문 스타일: 제목 Heading 1/2, 본문 Normal, 나열은 List Bullet. 문체는 "~한다/~이다" 평서형, 군더더기 없이. docx 생성은 `docx` 스킬(또는 venv `program/venv/wrb_voc` 의 python-docx).

## 2. 소스 주석 태그

```java
//	[결함34] 삭제된 VOC의 미결 결재 임의종결(CPACLOSE) — 결재함 좀비 결재 잔존 방지
```

- 형식: `//` + 탭 + `[결함NN]` + 무엇을 왜. 개선은 `[개선NN]`, 기능 단위 작업은 `[결재임의종결]` 같은 기능 태그. 날짜를 붙일 때는 `[260825]`(yyMMdd).
- JSP/XML 은 그 파일의 기존 주석 방식(`<%-- --%>`, `<!-- -->`)에 같은 태그.
- 한 파일에 여러 결함 수정분이 들어가면 블록마다 태그를 달아 결함별로 골라 반영할 수 있게 한다.

## 3. 수정소스 패키지 — `수정소스/<name>_<YYYYMMDD>.zip`

이름: `결함NN수정`, 여러 건 통합은 `결함01_03_09수정`, 기능 단위는 `결재회수정책수정`, 보안은 `보안CVE수정`.

```
결함34수정/
├─ README.txt
├─ 원본/            base(git HEAD) 시점 파일 — 파일명만(평면). 같은 이름이 겹치면 상위폴더명__파일명
├─ 수정본/          워킹트리 반영본
├─ patch/           01_<설명>.patch (+ _filelist.txt: 리포 상대경로 목록)
├─ DB/              NN_결함NN_<설명>.sql  (DB반영 폴더 사본. 번호는 DB반영 폴더의 다음 번호)
└─ 증적/            evid_01_수정전_….txt, evid_03_수정후_….txt (보안·응답 헤더 등 필요할 때)
```

줄끝: 고객사 반영 환경이 Windows 라 원본/수정본은 **CRLF 로 낸다** — NAS 워킹트리는 LF 이므로 스크립트에 `--eol crlf` 를 준다(README 에 "원본 : git HEAD 기준 (줄끝 CRLF 변환)" 으로 기록됨). patch 는 리포 기준 그대로다.

### README.txt 구성 (반영 담당자는 이것만 본다)

```
결함 NN (<한 줄 제목>) 소스 수정 산출물
==========================================================================

작성일 : yyyy-MM-dd
기준 브랜치 : wrb_voc_260701ver (기준 커밋 <short sha>)
원본 : git HEAD 기준 (줄끝 CRLF 변환)
수정본 : 워킹트리 반영본
태그 : [결함NN] … [yyMMdd]

1. 원인 요약          — 불릿 3~5개. 테이블.컬럼, 메서드명 수준으로 구체적으로
2. 수정 내용          — [A] [B] [C] 기능 단위로 묶고, 그 아래 파일별로 무엇을 바꿨는지
                        ※ 함정·주의(예: MyBatis OGNL 한 글자 비교)는 ※ 로
3. 선행 DB 반영 (필수) — 어떤 SQL 의 어느 STEP 을 소스 배포 전/후에 돌리는지, 안 돌리면 생기는 증상
4. 검증 (일자, 환경)   — 실제로 한 것만. 건수·응답 등 수치 포함. 미실행 항목은 사유와 함께
5. 주의 (파일 얽힘)    — 수정본에 다른 결함 수정분이 함께 들어 있으면 어떤 태그 블록만 반영해야 하는지
6. 파일 목록 (N)       — java / xml / jsp / sql 로 나눠 파일명 나열
```

해당 없는 절은 "해당 없음"으로 남긴다(3·5 절이 없다고 빼면 담당자가 확인을 못 한다).

메일로 전달하는 건은 `메일초안_<name>.md`, 변경 발췌본 `<name>_변경발췌_메일용.txt` 를 같이 넣은 전례가 있다 — 사용자가 "메일로 보낼 거"라고 하면 추가한다.
