# 결함 처리 (분석 → 수정 → 수정소스 패키지)

결함 1건은 **① 분석 문서 → ② 소스 수정 → ③ 검증 → ④ 수정소스 패키지** 순서로 끝난다. 사용자는 이 산출물을 고객사·내부망 반영 담당자에게 그대로 전달하므로, 형식이 지난 건들과 같아야 하고 내용은 소스 근거(파일:줄)로 뒷받침돼야 한다. 사용자가 일부 단계만 요청하면(예: "분석만", "zip만") 그 단계만 한다.

> **경로 해석**: 아래 `/volume2/claude/...` 는 NAS 기준이다. 다른 PC 에서는 `~/.ai-setup/paths.local.md` 의 경로 매핑 표를 따른다(Codex 는 자동 로드가 없으니 직접 읽는다)(참고자료 레포·소스 레포 위치가 PC 마다 다르다). 표에 없으면 사용자에게 묻는다. 스크립트는 이 스킬 폴더의 `scripts/` 에 있고 Windows 에서는 `python` 으로 실행한다.

## 0. 시작 전에 확인할 것

1. **프로젝트 판별** → 해당 참고 문서를 읽는다. 형식이 프로젝트마다 다르다.
   - 우리은행 VOC → `references/wrb_voc.md` (분석 docx 10절 + `수정소스/*.zip`)
   - SCBK VOC → `references/scbk_voc.md` (`수정/<날짜>/<건>/` 폴더 + 색인 표)
   - 그 외(스타벅스 등 형식이 아직 없는 프로젝트) → 그 프로젝트 참고자료 폴더에 기존 결함 산출물이 있는지 먼저 찾아 그 형식을 따르고, 없으면 wrb_voc 형식을 기본으로 쓰되 사용자에게 한 줄로 알린다.
2. **결함 원문**: 결함 목록 엑셀·메일·회의록 등 원문을 참고자료 폴더(`/volume2/claude/<프로젝트>/`)에서 찾는다. 원문이 없으면 사용자에게 받는다 — 원문 없이 추측으로 분석하지 않는다.
3. **같은 결함의 기존 산출물**: 분석 문서·이전 수정 zip 이 이미 있으면 읽고 이어서 작업한다(재분석·형식 불일치 방지). 연관 결함 번호도 확인한다.
4. 소스는 `/volume2/claude/repo/<리포>/`, 브랜치는 프로젝트 CLAUDE.md 기준. 작업 전 `git status` 로 워킹트리에 다른 건의 수정분이 섞여 있는지 본다(패키지에 얽힘 주의를 써야 한다).

## 1. 원인 분석

`systematic-debugging` 스킬 절차를 따른다: 증상 재현/확인 → 화면(JSP/JS) → Controller → Service → Mapper XML → 테이블/프로시저 순으로 데이터 흐름을 추적해 **근본 원인**을 특정한다. 증상 지점만 고치는 방안은 "임시 조치"로 구분해 적는다.

- 모든 주장에 근거를 단다: `파일명:줄` 또는 쿼리 id, 테이블.컬럼. 고객사가 "왜 그런가"를 되물었을 때 바로 답할 수 있어야 한다.
- DB 확인이 필요하면 프로젝트 CLAUDE.md 의 개발DB 접속 방법을 쓴다. **운영 DB·실데이터 변경 금지**, 조회 쿼리는 문서에 남긴다.
- 요건이 불명확해 결정이 필요한 부분은 추측으로 메우지 말고 "요건 확정 필요"로 분리한다.
- 같은 패턴이 다른 화면·쿼리에도 있는지 검색해 "동일 패턴 점검" 결과를 붙인다(한 건 고치고 같은 결함이 다시 접수되는 것을 막는다).

분석 문서는 프로젝트 참고 문서의 목차를 그대로 쓴다. docx 가 필요하면 `docx` 스킬을 사용한다.

## 2. 소스 수정

사용자가 수정을 요청했을 때만 한다(분석만 요청받았으면 수정 방안까지 문서에 쓰고 멈춘다).

- 공통 룰(`/volume2/claude/CLAUDE.md`): 기존 소스 스타일 유지, 요청 없는 리팩토링 금지, 주석은 사람이 쓴 것처럼, **커밋/푸시는 사용자 승인 후**.
- 수정 블록마다 프로젝트의 **주석 태그**를 단다(참고 문서 참조). 태그는 나중에 여러 결함 수정분이 한 파일에 섞였을 때 "이 결함 분만 반영"할 수 있게 해 주는 유일한 표식이다.
- DB 변경(공통코드, 인덱스, 데이터 보정)은 소스와 분리해 SQL 파일로 만든다: 적용·검증·원복을 구분하고, 소스 배포보다 먼저 돌려야 하면 "선행"이라고 명시한다.

## 3. 검증

`verification-before-completion` 원칙: 돌려 보지 않은 것은 "검증됨"이라고 쓰지 않는다.

- 최소: 컴파일(`mvn -q compile` 등) 통과, Mapper XML well-formed.
- 가능하면 로컬 기동 후 재현 절차를 다시 수행한다. 화면 회귀는 WIGO Web Tester(`wwt`)에 해당 결함 시나리오가 있으면 그것을 돌린다(전역 CLAUDE.md "웹 메뉴 테스트"). 오래 걸리는 빌드·기동은 `bgrun`.
- **실행하지 못한 검증은 "미실행 + 사유"로 그대로 적는다**(예: 공통코드 미존재로 실제 저장은 미실행). 패키지 README 의 검증 절은 실제로 한 것만 쓴다.

## 4. 수정소스 패키지

파일 수집·patch·zip 은 스크립트로 한다 — 손으로 복사하면 누락·인코딩 깨짐이 생긴다.

```bash
python3 <이 스킬 폴더>/scripts/make_fix_package.py \
  --repo /volume2/claude/repo/wrb_voc --name 결함34수정 \
  --out /volume2/claude/wrb_voc/수정소스 [--base HEAD] [--to WORKTREE|<커밋>] \
  [--files a.java b.xml ...] [--sql /path/06_xxx.sql ...] [--evidence /path/evid.txt ...] \
  [--layout wrb|scbk] [--eol crlf] [--no-zip]
```

- `--files` 생략 시 `base..to` 의 변경 파일 전체(추적 중인 수정 + 신규 파일). 다른 결함 수정분이 워킹트리에 섞여 있으면 반드시 `--files` 로 이 결함 파일만 지정한다.
- 결과: `원본/`(base 시점) · `수정본/`(변경 후) · `patch/01_<name>.patch` · `patch/_filelist.txt` · `DB/` · `증적/` · `README.txt` 골격 → zip(한글 파일명 UTF-8, `<name>_<YYYYMMDD>.zip`). `--layout scbk` 는 `patch.diff` · `01_파일/`(경로 유지) · `02_DB/` · `README.md` 골격을 만든다.
- 스크립트는 골격만 만든다. **README 의 원인 요약·수정 내용·검증·주의(파일 얽힘)·선행 DB 는 직접 채운다** — 반영 담당자는 README 만 보고 작업한다. 채운 뒤 zip 을 다시 묶으려면 같은 명령에 `--rezip` 을 준다.
- 만든 뒤 zip 목록을 한 번 출력해 파일 수가 README 의 파일 목록과 맞는지 확인한다.

## 5. 마무리 보고

사용자에게는 짧게: 결론 한두 문장(근본 원인), 산출물 경로(분석 문서·패키지), 선행 DB 작업 유무, **미실행 검증·요건 확정 필요 항목**, 커밋 여부(승인 전에는 미커밋 상태임을 명시). SCBK 는 `수정/README.md` 색인 표에 한 줄 추가한다.
